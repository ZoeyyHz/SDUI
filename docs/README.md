# 产品需求文档 (PRD)： 动态 UI 引擎与可视化发布系统（代号：AgileUI）

**文档状态：** 初稿
**产品愿景：** 让 APP 的前端 UI 迭代彻底告别“重新编译与发版审核”，实现毫秒级的所见即所得。

## 一、 背景与业务痛点 (The "Why")

在传统的 Scrum 开发流程中，移动端（APP）的 UI/UX 修改面临极高的沉没成本。
*   **痛点场景：** 客户或业务方提出轻微的视觉或布局修改（如：“将首页促销模块移到顶部”、“更改按钮颜色”）。
*   **传统链路：** 设计师修改 Figma -> 开发重新修改代码 -> 重新编译打出安装包（Build Package） -> 安装到测试机 -> QA 回归测试 -> 提交 App Store 等待审核（数天） -> 用户更新。
*   **业务影响：** 链路长达数天至一周，严重拖累了市场响应速度；开发人员的时间被大量浪费在低价值的“挪动 UI”上；业务方因无法立刻看到成果而产生挫败感。

## 二、 产品定位与核心价值 (The "What")

**AgileUI** 是一套基于 **Server-Driven UI (SDUI, 服务端驱动 UI)** 理念构建的“动态排版引擎 + 可视化 CMS + AI 助手”。

*   **对业务/客户：** 提供一个极其简单的可视化画布或 AI 对话框，让他们能像搭积木一样自己调整原生 APP 的界面，点击“发布”，线上瞬间生效。
*   **对开发团队：** 开发人员只需一次性写好底层的“标准化组件（积木）”，彻底从高频的 UI 微调中解放出来，专注核心业务逻辑开发。

## 三、 目标用户与使用场景 (Target Users & Scenarios)

| 用户角色 | 场景描述 | 获得的核心价值 |
| :--- | :--- | :--- |
| **甲方客户 / 运营经理** | 遇到双十一大促，需要临时把首页的一个 Banner 图和商品列表换位置。直接在后台拖拽并发布。 | 极致的控制感与实时性（无需等产研排期）。 |
| **前端 / 客户端开发** | 以前每次改版都要加班对齐 UI。现在只负责维护基础组件库，不再接“改个颜色/间距”的需求。 | 减少脏活累活，提高工程质量。 |
| **产品经理 (PM)** | 随时可以进行页面的 A/B 测试，直接在后台配置两套 JSON 分发给不同用户群。 | 极速验证商业猜想，实现真正的敏捷。 |

## 四、 系统核心架构描述 (System Architecture)

系统分为三大核心模块，基于 **JSON** 作为唯一的数据通信标准（Source of Truth）。

1.  **C端 (Client-Side Rendering SDK)：** 一个嵌入在原生 APP (iOS/Android/Flutter) 中的解析引擎。它不写死 UI 排版，而是通过 API 拉取云端的 JSON 配置文件，动态渲染出对应的原生组件。
2.  **B端 (Visual CMS 后台)：** 一个基于 Web 的可视化操作台。用户在这里拖拽组件、修改属性，系统会在底层自动生成符合规范的 JSON 文件并保存到数据库。
3.  **AI Copilot (大模型引擎)：** 接入 LLM。允许用户直接输入自然语言，大模型将其解析并修改后台的 JSON 配置文件，联动更新 UI。

## 五、 核心功能需求详细描述 (Functional Requirements)

### 模块一：B端 - 可视化控制台 (Visual CMS)
这是非技术人员（客户/运营）直接使用的“遥控器”。

*   **[F-1.1] 模块化组件库面板：**
    *   提供预设的、由开发人员封装好的业务组件（如：商品卡片、轮播图、导航栏、图文横幅等）。
    *   **安全沙箱机制：** 组件的高度、排版方式必须在开发预设的规则内，禁止非技术人员进行破坏性的像素级绝对定位，确保不会“丑出边界”。
*   **[F-1.2] 所见即所得画布 (WYSIWYG Canvas)：**
    *   支持组件在画布上的上下拖拽排序。
    *   支持简单的嵌套（如在一个容器内放入左右两个卡片）。
    *   提供移动端/平板设备尺寸的实时预览。
*   **[F-1.3] 属性配置面板：**
    *   **视觉配置：** 修改组件支持的特定属性（如：切换品牌主题色、修改文本内容、调整文字大小、更改图片 URL）。
    *   **数据绑定 (Data Binding)：** 允许给组件绑定动态数据源（如：按钮点击事件绑定“加入购物车”API；文本绑定 `{{user.name}}`）。
*   **[F-1.4] 版本控制与发布管理：**
    *   支持“一键发布到生产环境（热更新）”。
    *   支持生成每次发布的“版本快照”，一旦出现问题可“一键回滚”到上一版本。

### 模块二：AI Copilot 智能助手
让“连拖拽都嫌麻烦”的用户直接用嘴编程。

*   **[F-2.1] 对话式 UI 编辑：**
    *   用户输入：“把搜索框移动到最上面，并把背景改成节日红色。”
    *   AI 解析意图，转换为针对后台 JSON Schema 的 Diff 修改。
*   **[F-2.2] 防幻觉与预览机制：**
    *   AI 修改后，不直接上线，而是首先在 CMS 画布上渲染出预览效果。
    *   AI 只能修改已注册组件的 JSON 属性，无权凭空生成未知代码，100% 杜绝代码跑飞引起的 App 崩溃。

### 模块三：C端 - 动态渲染引擎 SDK
这是静默运行在用户手机里的核心。

*   **[F-3.1] JSON 动态解析与原生渲染：**
    *   APP 启动或刷新时，静默请求最新的 JSON 树，并映射为对应的原生 UI 控件。
*   **[F-3.2] 降级与缓存策略 (Fallback Mechanism)：**
    *   如果在无网、弱网环境下，或者 JSON 拉取失败，自动使用本地缓存的上一个可用版本的 JSON 进行渲染，确保 APP 永远不会出现白屏死机。
*   **[F-3.3] 业务逻辑解耦保持：**
    *   无论 JSON 怎么改变组件的位置，底层绑定的交互事件（如跳转页面、发起网络请求）必须保持可用。

## 六、 非功能性需求 (Non-Functional Requirements)

1.  **性能 (Performance)：** 
    *   C端解析 JSON 并完成页面渲染的时间必须在 **100ms** 以内，用户不能感知到明显的“拼装感”。
    *   JSON 配置文件需经过极致压缩，并配合 CDN 分发。
2.  **跨端一致性 (Consistency)：** 
    *   同一套 JSON，在 iOS 和 Android 端渲染出的视觉效果、间距比例必须高度一致。
3.  **安全性 (Security)：** 
    *   CMS 后台发布机制需具备权限控制（如：运营修改后，需项目经理审核后才能点击发布）。
    *   下发的 JSON 需增加数字签名校验，防止被中间人篡改（防止黑客下发恶意广告图）。

## 七、 项目实施与迭代路线图 (Roadmap)

**Phase 1：MVP（最小可行性产品）- 跑通闭环**
*   定义前后台通信的统一 JSON Schema 标准。
*   开发 5-10 个最高频的基础组件（按钮、图片、文本、列表）。
*   实现基础的 CMS 拖拽排序和 C 端热更新能力。
*   *目标：能不用重新发包就把 App 的首页改头换面。*

**Phase 2：深度整合与业务绑定 - 走向可用**
*   支持复杂组件嵌套和数据动态绑定（连接真实业务 API）。
*   加入多主题（Theme）支持，一键切换深色/浅色模式或节日皮肤。
*   完善 CMS 的版本回滚机制和操作日志。

**Phase 3：AI Copilot 赋能 - 终极形态**
*   接入大语言模型（如 GPT-4o 或 Claude）。
*   利用 RAG 技术让 AI 学习自家的 JSON Schema 规范。
*   实现“一句话改 UI”并实时呈现的终极体验。

## 八、 成功衡量指标 (Success Metrics)

1.  **发布周期时长 (Time-to-Market)：** 从 UI 修改需求提出到线上生效的时间，从原本的 **X 天** 缩短至 **Y 分钟**。
2.  **免发版热更率：** 在一个月内，不需要通过 App Store/Google Play 重新提交发版的 UI 迭代次数占比。
3.  **开发研发效能提升：** 开发团队处理“页面排版/视觉修改类”工单的时间成本下降百分比。
